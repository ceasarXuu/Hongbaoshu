# Pack Studio 产品需求文档

## 1. 背景

Hongbaoshu 2.0 已将 App 本体定位为阅读器，文本、音频、封面等内容通过资源包导入。当前仓库已经具备：

- Pack 格式规范
- `book.json` 结构约束
- Android 端导入与校验方向
- 若干文本转换与素材处理脚本

但资源包的生产流程仍以脚本和人工整理为主，存在以下问题：

- 电子书源格式不统一，导入前处理成本高
- 文本切句规则不可视，容易导致音频映射错位
- 音频制作链条与打包链条断裂，缺少统一中间产物
- 资源包问题通常在 Android 导入阶段才暴露，反馈过晚
- Win/macOS 双平台缺少统一、轻量、可复用的本地工具

为解决上述问题，规划新增独立子项目 `pack-studio`，作为本地 Web 形态的资源包制作工作台。

## 2. 产品目标

Pack Studio 的目标是：

1. 在 Win 和 macOS 上轻量运行，降低部署门槛。
2. 支持主流电子书格式导入，并统一转为 Hongbaoshu Pack 标准结构。
3. 提供可视化的文本结构预览、句子切分预览、音频映射校验。
4. 在打包前暴露结构错误、资源错误、命名错误，避免脏包进入 App。
5. 产出标准 `.hbs.zip` 资源包。
6. 一期输出句子 CSV，供外部音频制作软件批量读取。
7. 二期预留 Windows 本地 CosyVoice 3.0 接入能力。

## 3. 非目标

一期明确不做：

- 阅读器功能
- Android 导入界面复刻
- 账号、权限、云端协作
- 在线书库和远程分发
- 自动生成音频
- 自动修复电子书内容错误

## 4. 目标用户

主要用户：

- 资源包制作者
- 文本整理人员
- 音频制作人员
- 项目维护者

典型特征：

- 希望以低门槛方式把 `txt/epub/mobi` 转成项目资源包
- 需要明确的句子级导出结果
- 需要稳定的校验反馈和构建日志

## 5. 核心用户场景

### 5.1 场景 A：文本包制作

1. 用户新建一个打包项目。
2. 导入 `txt`、`epub` 或 `mobi` 文件。
3. 工具解析章节、段落、句子并生成中间结构。
4. 用户检查切句结果和书籍元数据。
5. 用户不导入音频，直接打包。
6. 工具输出纯文本 `.hbs.zip`。

### 5.2 场景 B：先导出 CSV，再外部制作音频

1. 用户导入电子书。
2. 工具切分句子并导出 CSV。
3. 音频团队用外部软件批量生成句子音频。
4. 用户把音频目录导回 Pack Studio。
5. 工具做句子 ID 映射和缺失校验。
6. 工具打包为带 narration 的 `.hbs.zip`。

### 5.3 场景 C：更新已有资源包

1. 用户打开已有项目。
2. 修改 `packVersion` 或素材。
3. 重新校验。
4. 输出新版本资源包。

## 6. 一期产品范围

### 6.1 必做能力

1. 项目管理
2. `txt/epub/mobi` 导入
3. 统一标准化为中间书籍模型
4. 章节、段落、句子预览
5. `packId / packVersion / title / author / edition` 编辑
6. 句子 CSV 导出
7. 音频目录导入
8. 音频映射校验
9. Pack 全量校验
10. 标准 `.hbs.zip` 打包
11. 构建日志与校验报告落盘

### 6.2 可做但不作为一期交付门槛

1. 封面自动提取
2. 音效资源导入
3. 章节切分规则少量可配置
4. 简单项目搜索与过滤

## 7. 二期方向

二期聚焦音频生成：

1. 仅优先支持 Windows
2. 接入开源 CosyVoice 3.0
3. 以插件方式提供 TTS 能力
4. 基于句子模型或 CSV 生成 narration 音频
5. 生成后回流到现有映射校验与打包链路

原则：

- 二期不得破坏一期无 TTS 情况下的完整闭环
- TTS 是增强能力，不是打包主链路前提

## 8. 运行环境要求

### 8.1 设计目标

- Win/macOS 双平台兼容
- 本地部署简单
- 本地文件系统可读写
- 不依赖云端服务

### 8.2 运行形态

建议采用：

- 本地 Web 服务
- 浏览器访问本机地址
- 所有项目数据存储在本地工作区

不要求一期必须封装成桌面壳，但架构要为后续 Electron/Tauri 封装留余地。

## 9. 页面范围

一期页面建议控制为 6 页：

1. 项目列表页
2. 导入页
3. 内容页
4. 音频页
5. 校验页
6. 构建页

### 9.1 项目列表页

展示内容：

- 项目名称
- 来源格式
- 最近更新时间
- 当前状态
- 最近一次构建结果

操作：

- 新建项目
- 打开项目
- 删除项目

### 9.2 导入页

展示内容：

- 源文件路径
- 识别到的格式
- 导入摘要

操作：

- 上传 `txt/epub/mobi`
- 重新导入

### 9.3 内容页

展示内容：

- 书籍元数据
- 章节列表
- 段落预览
- 句子切分预览

操作：

- 编辑元数据
- 查看 ID
- 触发标准化

### 9.4 音频页

展示内容：

- 句子总数
- 音频覆盖率
- 缺失句子数
- 孤儿音频数

操作：

- 导出 CSV
- 导入音频目录
- 触发音频映射校验

### 9.5 校验页

展示内容：

- 错误
- 警告
- 提示
- 资源完整性摘要

操作：

- 全量校验
- 查看阻塞打包项

### 9.6 构建页

展示内容：

- 实时日志
- 产物路径
- 构建摘要

操作：

- 触发打包
- 下载 `.hbs.zip`
- 查看历史构建记录

## 10. 项目状态模型

项目状态建议定义为：

- `draft`
- `imported`
- `normalized`
- `audio_pending`
- `ready_to_build`
- `build_failed`
- `built`

状态迁移由系统驱动，不提供用户手动修改入口。

## 11. 成功标准

一期成功标准：

1. 用户可从 `txt/epub/mobi` 完成一次标准资源包打包闭环。
2. 用户可得到句子级 CSV，用于外部音频制作。
3. 用户可导回音频并看到准确的映射校验结果。
4. 工具能在打包前阻止结构错误资源包输出。
5. 关键任务都有日志与 JSON 报告。
6. Win 和 macOS 均可通过本地方式启动。

## 12. 风险与约束

### 12.1 主要风险

1. `mobi` 结构解析稳定性弱于 `epub`
2. 句子切分规则漂移会直接破坏音频映射
3. 双平台文件路径与编码处理容易出现兼容问题
4. 二期 TTS 依赖复杂，不能侵入一期主链路

### 12.2 约束

1. 输出包必须兼容现有 `Pack` 规范
2. 打包前必须进行校验
3. 所有关键任务必须落日志
4. 每个小主题完成后应及时提交，保持开发轨迹清晰
